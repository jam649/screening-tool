## CSL bulk and source metadata

The [official CSL page](https://www.trade.gov/consolidated-screening-list) links the [public bulk JSON](https://data.trade.gov/downloadable_consolidated_screening_list/v1/consolidated.json). A TLS-verified system `curl` read returned 33,844,180 bytes, SHA-256 `f9807c77aa5e2f90b9566e043859baba98189e2b48ef87637007c8020dd71ba2`, and 26,128 results. Python's default local trust store failed certificate-chain verification; TLS verification was preserved by using the system curl trust store.

The envelope is an object containing `results`, `search_performed_at`, `sources_used`, `offset`, and `total`. Parse `results`, not the top-level object as a record array. `sources_used` already supplies 13 metadata objects with `source`, `last_imported`, `source_last_updated`, and `import_rate`; the observed timestamps include explicit UTC offsets and import rate is `Hourly`. FSE metadata exists even though no current FSE rows were present. Preserve stamps from the bulk independently of the optional API.

Observed row contract:

| Published field | Meaning for the app |
| --- | --- |
| `id` | Published listing identifier; preserve exactly. IDs overlap across sources: identity is `(source_list, id)`. |
| `source` | Verbose source name, including abbreviation; use an explicit abbreviation mapping. |
| `name` | String. |
| `alt_names` | List or null; absent/null becomes an empty list. |
| `programs` | List. |
| `addresses` | Optional list of objects: `address`, `city`, `state`, `postal_code`, `country`; values can be null. |
| `country` | Optional scalar residency country string; also use address countries. Preserve nationality/citizenship as distinct raw facts. |
| `type` | Optional string; not every source supplies it. |
| `remarks` | Optional string or null. |
| `federal_register_notice` | Text citation, not necessarily a URL; observed `Vol. 59, No. 44, 03/07/1994`. |
| `source_list_url`, `source_information_url` | Published links; preserve both and allow only valid http(s) links in UI/export. |

The full-file parser smoke found **96 published IDs shared across different sources**. For example, id `17014` occurs in NS-MBS and SSI; id `9647` occurs in PLC and SDN. Keep all 26,128 rows, use source plus published id as identity, and reject duplicates only within that composite key. This corrects the design's global-ID uniqueness assumption.

Other observed fields include `ids`, `entity_number`, dates/places of birth, title, license policy/requirement, dates, standard order, and vessel fields. Retain the complete raw row for future evidence. Current result sources: CAP, CMIC, DPL, DTC, EL, ACN, NS-MBS, MEU, PLC, SDN, SSI, UVL. Do not require every metadata source to have a result.

**Version identity:** `search_performed_at` and `last_imported` are volatile envelope metadata. Whole-file hashing is required for fetch provenance, but can create versions without entry changes. Retain the raw file hash and additionally compare a canonical record-set hash for version reuse; audit successful repeated fetches. This is an implementation implication of the observed envelope, not an ITA guarantee.

[Sources API candidate](https://data.trade.gov/consolidated_screening_list/v1/sources) was read without a credential and returned HTTP 401 with a missing-subscription-key message. The [official portal onboarding](https://developer.trade.gov/) verifies subscriptions and primary/secondary keys. Sending the explicitly nonsecret placeholder `subscription-key: schema-verification-invalid` changed the response from missing to **invalid subscription key**, verifying that this exact header is recognized. Successful authenticated access and response shape remain **unverified**: the official portal's API details widget is JavaScript-rendered and did not expose operation schemas through the text browser. Confirm the successful response using its Try it tool and a user-owned key. Do not call the old `api.trade.gov` route or fabricate source dates. Bulk metadata is the verified fallback.

## EAR retention

[15 CFR 762.6](https://www.ecfr.gov/current/title-15/subtitle-B/chapter-VII/subchapter-C/part-762/section-762.6), displayed current through 2026-10-08, confirms five years for EAR-required records from the **latest applicable transaction event**, including export/services, known reexport/transfer/transshipment/diversion, transaction termination, or the specified boycott request. A formal or informal government request prevents destruction without agency written authorization, even beyond five years.

Keep indefinite retention as the default. A five-year configuration floor is a product safeguard; screening-date age alone does not prove compliance with transaction-based deadlines. Any future purge requires dependency preservation and a legal-hold mechanism or must remain disabled when a hold cannot be excluded. The tool does not observe all transaction events.

## QuickBooks Online

The [official OAuth documentation, static rendering](https://static.developer.intuit.com/output_html/qbo/docs/develop/authentication-and-authorization/oauth-2.0.html) was read with TLS-verified curl because the interactive developer site returned a JavaScript shell; the core contracts were checked again for milestone 6 on 2026-10-14. Authorization: `https://appcenter.intuit.com/connect/oauth2`; token exchange/refresh: `https://oauth.platform.intuit.com/oauth2/v1/tokens/bearer`; scope: `com.intuit.quickbooks.accounting`. Authorization code flow uses a registered matching redirect URI, random checked `state`, and callback `realmId`. The token endpoint uses form encoding and Basic client authentication. The documented access lifetime is 3,600 seconds and rolling refresh lifetime is 100 days; the implementation stores the actual returned tokens and `expires_in`, `x_refresh_token_expires_in`, and optional `x_refresh_token_hard_expires_in` values rather than assuming perpetual refresh.

The same official OAuth page documents **POST `https://developer.api.intuit.com/v2/oauth2/tokens/revoke`**, Basic client authentication, `Content-Type: application/json`, and JSON `{ "token": "<token to revoke>" }`. This is the implemented revocation endpoint; no endpoint is inferred from the accounting API origin. Accounting requests use only the fixed HTTPS origins `https://sandbox-quickbooks.api.intuit.com` and `https://quickbooks.api.intuit.com`. Redirects and environment proxies are disabled. Read retries are bounded; ambiguous token POST failures are not blindly replayed because a grant may already have been consumed. Transport and vendor errors become safe codes without descriptions or credentials.

Implementation policy: app credentials are encrypted per environment and tokens are encrypted per source. OAuth state is hashed, bound to the exact live initiating Admin/session, expiry and app/source generations, and consumable once. Source realm binding remains permanent, including after disconnect; a different company requires a different source. Source operations share a persistent lease. No SQLite writer is held across token, query, CDC or revoke HTTP. Accepted refresh rotation persists in a short fenced system-maintenance transaction before further data requests, even if the initiating Admin is offboarded or disconnect intent arrives during HTTP. Realm, environment, client identity, generation and fence still must match; business data application separately rechecks active authority and connected status under its writer. App replacement rejects a live environment lease; an allowed same-client secret/verifier change atomically aligns existing encrypted credential generations.

A rejected new OAuth grant is never adopted as a connection. Best-effort revocation uses the verified endpoint; failed cleanup stores a bounded private encrypted backlog with the captured app identity and queues system cleanup. Accepted refresh rotation preserves the latest backlog read under its fence, including cleanup added while HTTP was in flight. Cleanup of an orphan grant preserves any valid existing connection. Final revocation commits compare current source generation and encrypted credential identity so a concurrent replacement cannot be cleared. These are product safety rules, not a vendor guarantee about exactly-once token requests.

[Query contract](https://static.developer.intuit.com/output_html/qbo/docs/learn/explore-the-quickbooks-online-api/data-queries.html), read with curl, permits `GET /v3/company/{realmId}/query?query=...`, with `STARTPOSITION` and `MAXRESULTS`. Default size is 100, maximum 1,000. Enumerate each entity until exhausted. Active/inactive list objects require explicit `WHERE Active IN (true, false)` when reconciling all records. Namespaces must include entity type because Customer and Vendor IDs can overlap. Map inactive objects to local soft deletion; map reactivation back to active.

Milestone 6 requires every Customer and Vendor page to validate before a batch is marked complete. It rejects unexpected entity keys, duplicate identities, invalid numeric counts and contradictory/incomplete page metadata instead of treating missing records as deletions. Local IDs are `Customer:<Id>` and `Vendor:<Id>` within a source. Product mapping policy uses `CompanyName` for companies; otherwise explicit personal-name fields identify an individual, while `DisplayName` alone conservatively defaults to company. `DisplayName` and `PrintOnCheckName` can be aliases; a company's contact name and hierarchical `FullyQualifiedName` remain raw facts. `BillAddr` supplies primary locality, with `ShipAddr` as fallback, while both street-line sets and the complete original object are retained. Inactive objects and CDC tombstones carry identity only and never overwrite the historical name/raw record with blank fields. Type participates in matching hash rule v2. The design §5.4 unchanged-hash no-write rule remains explicit: role, phone/raw metadata and canonical-equivalent display changes do not replace the last applied party or trigger screening. Source identity and health remain independently recorded.

[CDC documentation](https://static.developer.intuit.com/output_html/qbo/docs/learn/explore-the-quickbooks-online-api/change-data-capture.html) and [Intuit's official CDC article](https://medium.com/intuitdev/building-smarter-with-intuit-stay-in-sync-with-cdc-171f8094dd37) confirm `GET /v3/company/{realmId}/cdc?entities=customer,vendor&changedSince={timestamp}`, a 30-day lookback, full changed-entity payloads, and a 1,000-object response cap. Shape: `CDCResponse[] -> QueryResponse[] -> Customer[] / Vendor[]`; deleted entities can carry `status: Deleted`. Do not advance the cursor on incomplete or capped results. Use full reconciliation after a gap beyond the window, and fail/reconcile on saturation rather than silently skipping changes. No pagination contract for CDC was verified; query pagination belongs to full enumeration.

The official CDC example puts a cumulative `totalCount` on the last entity node; it is not necessarily that node's local count. Its no-change example contains `QueryResponse: [{}]`. The parser accepts these documented shapes with provable counts. Saturation or unverifiable completeness triggers a separately validated full query snapshot; malformed schemas and failed requests abort. The implemented five-minute overlap and poll-start cursor are conservative product choices. Missing, malformed or future cursors, or an overlap-adjusted gap of at least 30 days, use full reconciliation. Partial failures leave parties, cursor and screening tasks unchanged; an already accepted and durably stored rotating token remains preserved.

[Webhook configuration and signatures](https://static.developer.intuit.com/output_html/qbo/docs/develop/webhooks/configure-webhooks.html): compare `intuit-signature` with Base64(HMAC-SHA256(verifier-token, **raw request body bytes**)) using constant-time comparison. Configure sandbox/production verifier tokens separately. Reject invalid signatures before parsing or scheduling. Valid events should trigger a CDC poll and be idempotent, with the configured realm enforced.

[Mandatory CloudEvents migration](https://medium.com/intuitdev/upcoming-change-to-webhooks-payload-structure-2a87dab642d0) extended its deadline to **2026-07-31**. Current webhook payload is a JSON **array** of events with `id`, `type` (such as `qbo.customer.updated.v1`), `time`, `intuitentityid`, and `intuitaccountid` (realm), plus CloudEvents fields. Support this contract; legacy `eventNotifications` is optional compatibility, not the current sole format. Five-minute delivery is not a latency guarantee.

[CloudEvents 1.0.2, required `id` and `source` attributes](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#required-attributes), verified on 2026-10-14, defines event identity by the combination of `source` and `id`, not `id` alone; duplicate deliveries can reuse that pair. The implemented receipt digest adds environment, configured app identity and realm to that pair. Signed events are bounded and authenticated before parsing, then receipt deduplication and poll enqueue occur atomically under a short writer. Webhook fields never become party data. An equivalent already queued poll is reused; a running poll cannot absorb a later receipt, which retains a durable follow-up. A busy source lease leaves deferred work queued for recovery. Only connected, credentialed sources are scheduled; source health displays the actual persistent schedule's next run.

The [synthetic QBO fixtures](../../fixtures/qbo/README.md) and milestone 6 tests exercise these contracts through injected memory transports and isolated databases, including actual scoped screening against the unchanged CSL fixtures. They are manually authored dummy official-contract-derived responses, **not live recordings, VCR cassettes or sandbox/customer evidence**. Tokens, code, state, verifier values, client secrets and orphan-cleanup credentials are excluded from public source/settings payloads, audits, operation parameters and exports. SQL/ORM guards freeze OAuth provenance and permit only its first consumption; logout removes the live session without erasing that evidence. Live OAuth, pagination, CDC and CloudEvents validation remains deferred by the user; see [milestone 6 evidence](../milestones/6.md) for the separate local gate status.

[Official production/private-use requirements](https://static.developer.intuit.com/output_html/qbo/docs/go-live/publish-app.html), read with curl, require Production App Details (including EULA/privacy and application URLs), profile, OAuth setup, and **approved App Assessment Questionnaire** before Show Credentials appears. The page explicitly allows private use after production credentials; marketplace listing is separate. This supports a self-hoster-owned app path, but does not guarantee any specific applicant's approval. [Partner Program guide](https://static.developer.intuit.com/resources/Intuit_App_Partner_Program_Guide.pdf) distinguishes production assessment from additional marketplace security/technical/marketing reviews. Document current quotas/billing from the applicant's dashboard before production use; do not promise unlimited free calls.

## Business Central

Verified again for milestone 7 on 2026-10-14; live tenant validation remains deferred. [Microsoft S2S authentication](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/automation-apis-using-s2s-authentication) supports client credentials for unattended standard API access: Application `API.ReadWrite.All`, tenant consent and an enabled BC Entra application with restricted object permissions. `Automation.ReadWrite.All` serves automation routes, which this connector does not call. Applications cannot receive `SUPER`; exact restricted permission sets remain a tenant check. The client-credentials integration does not require a user authorization redirect, refresh token or app logout/revoke endpoint.

The [Entra grant](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow) posts client ID/secret, `grant_type=client_credentials` and scope `https://api.businesscentral.dynamics.com/.default` to `https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token`. Retain the actual opaque Bearer and supplied positive `expires_in`. The [current standard endpoint](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/api-endpoint-structure) is `https://api.businesscentral.dynamics.com/v2.0/{tenantId}/{environment}/api/v2.0`; companies/customer/vendor/subscription paths append to it. UUID-only tenant/company/entity acceptance is a product restriction. [Environment constraints](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/administration-center-api_environments) are fewer than 30 characters, alphabetic first and then letters/digits/underscore/dash. Preserve configured routing case; conservatively case-fold company-binding uniqueness without claiming Microsoft's case behavior is verified.

[Customer](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_customer) provides Company/Person type; the [standard vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendor) has no equivalent and defaults company in this product. Preserve `id`, `displayName`, locality/address fields, `lastModifiedDateTime` and complete raw objects. `blocked` restricts posting and never soft-deletes a party. [Server paging](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/webservices/server-driven-paging-in-odata-web-services) supports `Prefer: odata.maxpagesize=300`; `$top=300` would cap the whole collection. Follow actual opaque continuations with the same fixed origin and exact tenant/environment/company/resource collection path, including bounds/counts/duplicates/completeness before apply. Timestamp filtering uses a five-minute overlap and poll-start cursor. Daily complete ID reconciliation and deletion/collection-triggered full polling are product policies for hard deletions; no BC 30-day retained-CDC horizon was verified. Invalid content/pages fail visibly and atomically.

The [subscription lifecycle](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/dynamics-subscriptions) defines create and renewal handshakes, actual `expirationDateTime`, three-day expiry, default 30-second delivery delay and retry for up to 36 hours only on 408/429/5xx. A persistent 12-hour reconciliation interval and renewal below 36 hours remaining are product choices. Notifications are only authenticated polling signals; payload records and arbitrary resource URLs are never applied or fetched.

[Create](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/api/dynamics_subscriptions_create) returns 201 with actual opaque string `subscriptionId`, not a GUID. [Renew](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/api/dynamics_subscriptions_update) uses PATCH to `B/subscriptions('{escaped-string-key}')`, required `If-Match` and actual 200 response; [delete](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/api/dynamics_subscriptions_delete) uses the quoted key/ETag and no body, returning 204. Some examples retain v1.0 paths; use the current standard v2.0 base. ETag response placement and real error variants remain live checks. Encrypted pre-POST intent and accepted-ID custody survive uncertainty, delayed visibility, offboarding and cleanup failure. Definite rejected creation, trusted absence/actual expiry, conflict retry and per-obligation progress are distinguished without blind duplicate POST or dropping known ownership.

The BC-linked [Microsoft handshake guideline §15.5](https://github.com/microsoft/api-guidelines/blob/vNext/graph/Guidelines-deprecated.md#155-verifying-subscriptions) specifies anonymous POST with query `validationToken`, potentially empty body and optional ClientState header; echo its sole decoded bounded text in HTTP 200 within five seconds. The route scrubs queries before URL/error handling and uses plain text/no-store/no-referrer/no-sniff. Notifications authenticate every registered private client state/resource outside the writer, then recheck connection/generation/subscription authority inside a short atomic receipt/poll writer. Public-address changes queue cleanup/rebind immediately; non-HTTPS disables webhook delivery while retaining polling. Remote subscription cleanup preserves book/human evidence and does not claim to revoke Entra consent.

## Jev and Laya

Applied the available `typesafe-ai` skill and read its [live index](https://docs.typesafe.ai/llms.txt), [HTTP API](https://docs.typesafe.ai/api), and [Noul contract](https://docs.typesafe.ai/primitives/noul). Endpoint: `POST https://api.typesafe.ai/v1/systemone`, Bearer API key, JSON. Required `state` (string/object/array), `model`, and a named `questions` map. For a pair:

```json
{
  "state": {"party": {}, "listing": {}, "components": {}},
  "model": "jev-1.13.0",
  "questions": {
    "same_party": {
      "type": "noul",
      "instructions": "These two records refer to the same party."
    }
  }
}
```

Read `answers.same_party.noul` as a finite number in [0,1], confirm its `type`, and preserve the response model ID and token usage. Noul has no separate Jev confidence field. Invalid schema/nonfinite/out-of-range answers must cause deterministic fallback, not a zero score.

[Current models](https://docs.typesafe.ai/models): `jev-1.13.0`; `jev-latest` and `jev-preview` currently alias it. Budget 64k tokens for state plus all questions, and 32k for state plus longest question. Current published price $0.042/million input tokens; outputs free; published limits 80 requests/s and 100k tokens/s can change. Pin the model for reproducible evaluations. [Quickstart](https://docs.typesafe.ai/introduction/quickstart) directs users to the console for a key; actual account access/billing was not tested. Keep AI optional and do not assert that early-access enrollment is guaranteed or blocked.

[Laya publisher model card](https://huggingface.co/convaiinnovations/laya/raw/main/README.md), read via curl, confirms Apache 2.0, Python >=3.10, `pip install "laya[serve]"`, and `laya-serve` on `POST /v1/systemone`. Checkpoints: root English 512 tokens, multilingual 1,024 default with explicit `max_len=8192` support, typed-decisions 1,024. Defaults allocate 192/256 tokens to the question head, leaving approximately 320/768 state tokens. Token budgets include instructions; character-count trimming is not proof the state fits. Preserve the design's ordered trimming and record truncation.

[Publisher serving source](https://raw.githubusercontent.com/NandhaKishorM/laya/main/laya/serve.py) accepts the same state/questions shape and additional `model`/`max_len` controls. It binds 0.0.0.0:8000 without auth by default; configure local binding or `LAYA_API_KEY`. `LAYA_JEV_STRICT=1` projects responses to the Jev schema. Explicit `model: multilingual` avoids long English inputs selecting the 512-token checkpoint. The source reports caps for body/state/question counts and optional token budgets; use a pinned runtime and test its actual HTTP schema.

The publisher explicitly warns base checkpoints perform near chance on its typed-decisions benchmark and specialization improves results. Those results do not establish screening quality. Keep deterministic safety rails and require fixture/held-out comparison before trusting the default blend. This initial contract research did not download weights. The subsequent [local Laya validation](laya-validation.md) ran pinned weights against 120 labeled probes and a stress case. Its screening-quality results support deterministic weighting by default for the unspecialized local checkpoint.
