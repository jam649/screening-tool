# Milestone 3 — CSV and deterministic screening

Built and verified 2026-10-13. CSV/XLSX imports feed the same canonical party records used by deterministic screening. Every stored comparison retains the original party and government entry, component scores, aliases and normalized forms. AI is optional and no model is called in this milestone.

## Built

- Bounded CSV/XLSX previews, explicit column mapping, saved source mappings, strict country validation, rejected-row reporting, full-sync deletion reconciliation and canonical party hashes. Invalid rows abort the full snapshot so a rejected customer cannot disappear silently. Missing stable external IDs use deterministic generated IDs and show a warning that matching-field changes create a new party file.
- Shared NFKC/casefold normalization, Unicode and ASCII forms, configurable legal suffix removal, individual token-order variants and country conversion through pycountry. Hashes exclude phone numbers, raw connector metadata and role, following design section 4.1.
- Internal-UUID candidate indexing over primary names and aliases, shared-token and Double Metaphone blocks, and full-index fuzzy fallback when blocking finds fewer than three entries. Government IDs shared by different source lists remain separate records and pairings.
- Maximum pairwise name scoring using the specified 0.5 token-set / 0.25 token-sort / 0.25 partial weights; country +5/−15, city +5, address token overlap up to +5, type mismatch −10 and short-name −10, clamped to 0–100. Address overlap uses Jaccard similarity against the best entry address. All weights, suffixes, stopwords and source-list selection are included in the immutable run settings.
- Thresholds default to candidate minimum 50, review 65, likely 90. Scores below the candidate minimum are not stored. Low candidates remain visible in history and do not enter the queue. The deterministic likely rail is applied before insertion.
- Exact four-hash suppression produces a suppressed observation. Changed inputs produce new evidence linked to the previous disposition and a before/after explanation. Stored snapshots never read mutable current records to reconstruct historical comparisons.
- Atomic screening under a SQLite write lock; durable tasks commit status, run and comparisons together. Failed task errors are sanitized, no partial run remains, and a later invocation retries. List tasks compare their version's historical entry hash against the current record, skipping removed/replaced entries while preserving relevant deltas across newer versions.
- Admin-only `POST /api/v1/screen` accepts exactly `all: true` or `party_id`. Authenticated users can read `/screen/runs` and `/screen/runs/{id}`. CLI `screen --all`, `screen --party <uuid>` and `screen --changed` share the same implementation. Existing CSL commands remain available.

## Queue evidence and design decisions

The schema's three statuses cannot distinguish an unresolved repeated comparison from its original queue item. Each repeated observation therefore remains `status: open` and records `explanation.queue_anchor_hit_id`; only its referenced anchor represents work. No false-positive suppression or disposition is invented for an unresolved repeat. A scoring-settings fingerprint in `explanation.queue_context` prevents changed thresholds or weights from borrowing a stale confidence. A changed context creates a new anchor and keeps the old evidence unchanged.

`queue_hits(db)` is the canonical queue selector. It considers the most recent completed scope for a current party/entry pair, excludes removed/deleted/hash-stale records, resolves repeat observations to their anchor, and filters out low results. Run snapshots include the party/entry scope even when no candidate is stored, so raising the candidate threshold does not leave an older confidence in the active queue. Consumers must use this selector rather than count every historical `open` row. Later disposition handling must resolve the anchor and its repeated observations together.

The specified Unidecode package uses GPL licensing. The dependency is **text-unidecode 1.3 under its Artistic license option**, preserving both Unicode and ASCII representations while allowing the MIT distribution. Dependency provenance belongs in the project's third-party license documentation.

The user explicitly approved including type in both hashes on 2026-10-13. Hash rule version 2 includes `party_type` and canonical CSL `entity_type`, sharing Entity/Company and Person/Individual semantics with scoring. Type-only party edits now create source changes/tasks; type-only CSL edits create list deltas. Both invalidate remembered four-hash false positives and retain prior human history. Phone, role and raw metadata remain outside the hashes.

CSL matching fields use shared NFKC/casefold/punctuation/whitespace normalization and retain Unicode and ASCII forms. Legal suffixes remain in the hash so changing a company form remains a conservative invalidation. Aliases, addresses, countries and programs are sorted/deduplicated as unordered sets. Known countries become ISO2; unknown text is preserved rather than collapsing different unknown countries into one value. Formatting/case/width changes and set order do not invalidate a hash; meaningful address/program/type changes do. Original raw fields and formatting remain available in immutable snapshots. Completed scopes include actual `party_hashes` and `entry_hashes`, proving what was screened even when a v2 run refers to the unchanged raw file of a v1 historical version.

The explicit `screening-tool hashes upgrade` command validates the configured encryption key, rehashes current cache rows, audits old/new hashes, keeps old suppressions intact and queues one durable manual full screening. Operators of previous cached deployments must run this command and then `screening-tool screen --changed`. Upgrade does not execute the screening itself. Historical Hit/Disposition/CSLEntryRevision/CSLVersion rows remain unchanged, including their original v1 hashes and raw-file provenance. New runs record `hash_rule_version: 2`; reopening a legacy decision records `explanation.hash_rule_change`. A later fetch of unchanged government bytes may create a v2 semantic version with the same raw-file hash and zero factual listing changes; it never edits the old version. Screening refuses stale cached hashes with this explicit upgrade instruction. Automatic startup/other CLI-command rewrites were rejected by approval review, so migration runs only when the operator invokes its command. Tests execute it only against disposable synthetic databases; no actual customer cache was migrated.

## Failure modes and pending work

Common words, aliases and fuzzy scores can produce false positives; fixture success cannot prove every transliteration will be found. Full production-book performance and recall checks remain milestone 9 work. SQLite serializes writers, and a busy database returns a retryable screening error. Task failures keep durable work available for retry and do not expose exception text that might contain credentials.

The review UI/disposition workflow belongs to milestone 4, auto-clear/scheduling/report/export to milestone 5 and optional adjudicator implementations to milestone 8. The engine exposes an `AdjudicationHook` returning `Adjudication` before a Hit is inserted, so those later implementations cannot rewrite immutable scoring evidence. Live QuickBooks and Business Central sandboxes remain explicitly deferred; fixture gates do not claim live credential-dependent validation.
