## Contracts that already exist

`queue_hits(db)` is the current queue authority. Use its selection in the UI, dashboard and morning report rather than counting historical `Hit.status == open` rows. A repeated or superseded observation does not constitute another work item or a human clearance.

`reports.metrics.dashboard_metrics`, `party_screenings`, `current_screening_coverage`, `auto_clear_observations` and `removed_entry_closure_observations` are the shared fact layer. `last_report_at` is an aware UTC ISO timestamp for the last completely successful morning-report snapshot. Slider auto-clears have `slider_value_at_time != null`; removed-entry closures have no slider and remain a separate measure.

Every new run freezes exact `scope.party_ids`, `scope.party_hashes`, `scope.entry_ids` and `scope.entry_hashes`, scoring settings and hash-rule version. Current-list coverage requires all currently enabled listing inputs for the current party hash and scoring context; a delta alone cannot establish full coverage for a newly added party. Read-only run/audit listings project scope counts; dedicated full exports use the stored manifests. Projection must never mutate stored audit or run evidence.

False positives persist one suppression on the exact party ID, entry ID, party hash and entry hash, pointing to a real human decision. Hash changes reopen with the prior actor, note and real before/after input differences. Suppressed observations reference that original decision rather than creating a fake new disposition. Current confirmed/escalated decisions continue to govern identical repeats; the matching owner preserves that behavior.

## Persistent scheduler and command execution

Use the verified pinned APScheduler 3.11.3 release and one scheduler in the single API process. The implementation uses an allowlisted JSON `BaseJobStore` backed by SQLAlchemy tables in the existing SQLite store; it avoids executable pickle and persists only fixed callback arguments and validated cron/interval definitions. The [official scheduler guide](https://apscheduler.readthedocs.io/en/3.x/userguide.html) requires stable job IDs and globally accessible serializable callables; The standard [SQLAlchemyJobStore](https://apscheduler.readthedocs.io/en/3.x/modules/jobstores/sqlalchemy.html) documents the SQLite persistence integration; the application supplies its JSON serialization in place of pickle. Pass only nonsecret IDs and fixed command identifiers as job arguments. Do not serialize passwords, API keys, full customer records or application/session objects into scheduler jobs.

Register schedules after migrations and encryption-key validation. Start paused, reconcile jobs by stable ID, preserve an unchanged job's stored next-run time, remove schedules whose source no longer applies, then resume. Changing a schedule deliberately recalculates its trigger and records an audit event. Startup must not reset every existing job into the future and lose a missed run. Configure coalescing and one instance per job, with a documented catch-up grace period; perform one durable recovery cycle on restart when monitoring was interrupted. Shut down the scheduler before disposing its engine.

| Stable job ID | Default | Operator command and behavior |
| --- | --- | --- |
| `csl-daily` | Daily 05:00 in configured IANA timezone; server timezone initially, UTC fallback | `screening-tool csl refresh`; successful added/changed entries enqueue scoped list work; removed entries close through immutable system decisions |
| `source-<uuid>` | Every 15 minutes for configured QBO/BC sources | `screening-tool sync <uuid>`; CSV remains an explicit upload/manual sync, never an invented remote poll |
| `screen-recovery` | Immediately after successful refresh/sync and a short recovery polling interval | `screening-tool screen --changed`; consume durable pending/failed work atomically, with actual current inputs |
| `morning-daily` | Daily 07:00 in configured timezone | `screening-tool report send` |
| `outbox-recovery` | Immediately after a committed run and periodically for recoverable retries | `screening-tool alert send` |
| `retention-weekly` | Weekly | `screening-tool retention apply`; disabled policy exits without deleting data |

Each scheduled operation must be runnable through its documented CLI command. Keep one business implementation behind API, CLI and scheduler entrypoints. A global serialized scheduler dispatch callable may invoke the fixed console command argument list without a shell; alternatively the common command dispatcher must exercise the same command implementation. Capture sanitized status, not full customer-bearing command output. Never put credentials in arguments. API/CLI operator invocations also use the same persistent overlap protection.

Add durable leases with operation key, random owner ID, acquired/expiry timestamps and heartbeat for long work. Acquire/recover under a short `BEGIN IMMEDIATE`; release only by the owning operation. A held live lease logs an overlap skip and exits. Expiry cannot cause a second long-running screening while the first owner is still working: heartbeat and fencing checks protect completion. Download, ERP and SMTP network calls must not hold SQLite's global writer lock. The engine retains its atomic writer transaction for evidence/run completion.

Persist operation attempts and sanitized health: start, finish, outcome, linked run/fetch/source/report IDs and retry eligibility. An interrupted attempt survives restart and can be retried without partial comparisons or double-applying a completed task. Scheduler serialization and application leases supplement the existing CSL fetch lease and engine transaction.

Full-book screening happens on first usable list/book load, explicit manual request, an explicit hash-policy upgrade, and a scoring-configuration change. Normal monitoring processes list deltas and changed/new parties. A CSV source added before a list must receive its initial full screening once a list becomes available. A successful empty CSV full snapshot still soft-deletes every absent party; malformed/rejected/partial files must not reconcile deletions.

## Auto-clear and scoring settings

Canonical public fields: `auto_clear_enabled` defaults `false`; `auto_clear_threshold` is an integer bounded inclusively by current review and likely thresholds. Preserve the established candidate/review/likely ordering. Enabling requires the exact acknowledgment string `I understand`, an active Admin, CSRF, and an immutable audit event naming the actor, chosen threshold and notice. Subsequent slider/enabled changes are audited. A conflicting threshold change must require a valid joint update rather than silently clamp the slider.

Freeze the auto-clear policy before each run. Only a newly inserted, otherwise open `review` observation with confidence strictly below the frozen value qualifies. Apply the deterministic likely rail first. Low, likely and exact-human-suppressed observations never receive slider decisions. The system decision has actor null, the frozen slider, run ID, model identity or deterministic-only designation, deterministic score and final confidence in its note. Insert and flush the immutable decision before transitioning the hit status. The hit and decision commit with run counters and policy provenance.

Auto-clearing a new observation does not create a false-positive suppression. Slider changes do not mutate prior hits or decisions and do not immediately re-screen the book solely to alter past outcomes. Keep auto-clear policy separate from the matching queue fingerprint so an unrelated slider move cannot manufacture new matching anchors. Changes to actual matching thresholds, weights, suffixes, stopwords or enabled lists enqueue one durable full task atomically with the audited setting update; old comparisons remain historical.

Proposed dedicated API: `GET/PATCH /api/v1/settings/auto-clear`. PATCH accepts `{enabled, threshold, acknowledgment?}` with the exact acknowledgment required on an off-to-on transition. GET returns enabled/threshold, current min/max and the notice. The matching owner may expose equivalent canonical flat fields through the existing settings response, but there must be one validation path and one stored key naming convention.

## SMTP, invitation delivery and reports

Provide a dedicated Admin `GET/PATCH /api/v1/settings/notifications` for host, port, TLS mode, username, optional replacement password, from address, recipients, morning time, immediate-likely switch and the public HTTPS base URL used in links. Reads return only whether secrets are configured; writes encrypt the password with existing Fernet handling. Audit changes redact secret values and the encryption envelope. Validate addresses, port, time and URL; prevent header injection. Preserve an existing password when the replacement is omitted and require an explicit clear operation to remove it.

Use Python's [SMTP client](https://docs.python.org/3.12/library/smtplib.html), verified TLS contexts, bounded connection/read timeouts, and STARTTLS or implicit TLS by default. Never authenticate over plaintext. Local fixture SMTP may use anonymous plaintext explicitly. No transport debug logging or exception text that could disclose credentials, MIME bodies or invitation tokens. Failed delivery records a sanitized category and a UI banner; it never rolls back a completed screening run.

Create durable outbox batches and per-recipient deliveries. A batch freezes as-of facts, the report window and the actual records needed to render its text and HTML alternatives. Sensitive invitation payloads containing the raw fragment link must be encrypted in the outbox, never in ordinary audit fields; scheduler arguments contain only delivery IDs. Stable batch/recipient keys and Message-ID reduce duplicate delivery on retries. SMTP does not guarantee exactly-once delivery across a crash after server acceptance: record an uncertain outcome and expose that limitation without falsely recording success.

A morning report uses one fixed `window_end`/as-of timestamp. Subject: `<display_name>: <n> open items, <m> likely matches`. Body order: CSL identity and latest successful fetch time; current open count with queue link; current likely party/list names; new matching anchors in the report window; slider auto-clears in that window with the same party filter; removed-list closure count separately; aggregate list added/changed/removed counts in the window; all stale/failed source syncs; exact ITA disclaimer footer. Emit a short no-change line when appropriate and still send the message. Never render an exact false-positive suppression or a repeated anchor as a new human clearance.

Send one message per configured recipient, with plain text and HTML alternatives. Advance `last_report_at` to the batch's fixed `window_end` only after every recipient delivery succeeds. A partial failure preserves successful-recipient delivery records and retries only failed recipients; a retry uses the original frozen body. Events arriving after `window_end` belong to the next report. A failed test email or immediate alert never advances the morning boundary. Recipients-empty/SMTP-unconfigured is a visible configuration state, not a successful send.

Immediate alerts are off by default. Transactionally enqueue one alert batch per committed run with its eligible likely observations; deliver after commit, one message per recipient per run. Section 9.4 literally says all likely hits written by that run, so the implementation must not silently substitute only new queue anchors. Include a hit's current/repeated/suppressed status and original decision context when applicable, rather than implying a previously marked false positive is a new confirmed match. Any deliberate narrower alert policy must be an explicit documented product decision by the coordinator.

Invitation creation uses the existing random one-use fragment token, digest, expiry and manual link. With SMTP configured, queue encrypted invitation delivery immediately and return delivery status plus a manual fallback on failure. Validate issuer authority again at acceptance; offboarding an issuer revokes their pending invitations. Never place invitation tokens in paths/queries, logs or audit records. An explicitly requested local fixture report/invitation email is sufficient for the gate; no live customer recipient must receive an unsolicited validation message.

API contracts: `GET /api/v1/monitoring/status` returns schedule/operation health and next runs; Admin `POST /monitoring/cycle` enqueues an immediate persistent fixture/operator cycle and returns an operation ID. Admin `POST /notifications/test` sends to an explicitly supplied validated test recipient. Admin `POST /reports/morning/send` returns batch ID/status and per-recipient delivery outcomes; `GET /reports/morning/status` returns last successful boundary and pending/failure health. All unsafe authenticated methods require CSRF. Expose asynchronous status honestly: enqueued is not delivered.

## Audit exports

Authenticated endpoints: `/parties/{id}/export?format=pdf|csv`, `/runs/{id}/export?format=pdf|csv`, `/exports/parties.csv` with exactly the current party-list filters, and `/exports/full.zip`. The current-view CSV exports every matching row, not just the visible pagination page. Reuse `filter_party_rows` and its role/source/country/status/stale/auto-clear/soft-delete semantics; retain `unscreened` and `escalated` labels.

Per-party and per-run exports use stored hit snapshots, decisions, their original actor identities, scoring/model settings, exact party and entry hashes, hash-rule version, actual run scope, timestamps and relevant append-only audit events. Never fetch mutable current parties/listings to substitute for past comparison inputs. Current-record sections must be explicitly labeled current. Include zero-hit participation and suppressed groups with the original human suppression decision.

For zero-hit history, preserve actual per-party run evidence. New runs should capture immutable party snapshots in a dedicated run-party evidence table or an equivalent immutable manifest; avoid duplicating a whole book into every hit. Legacy events may use a real prior `parties.create/update` audit snapshot that matches the recorded party hash and event time. If no genuine snapshot exists, print that historical fields are unavailable and preserve the known hashes/membership; never reconstruct historical fields from today's record. An entry hash manifest after an explicit hash-policy upgrade is the actual comparison authority even if the linked old version's original revision uses the older hash rule.

Include complete relevant party/source/list version/fetch/run/task/decision/suppression/settings provenance. Preserve matched-token explanations. PDF needs safe escaped text, readable page breaks and the exact ITA notice in every export footer. CSV must quote correctly and neutralize spreadsheet formula prefixes, including leading whitespace/control variants. ZIP filenames use internal IDs or safely sanitized names, never path traversal. Source links prefer safe Federal Register URLs, then safe source-list URLs. Responses use attachment headers, safe filenames and no-store caching; large ZIP generation must not expose transient files outside private ignored runtime storage.

The full ZIP contains every party file, including soft-deleted parties, and complete run/audit indexes and a manifest with export timestamp, selection, schema/hash policy and SHA-256 checksums. Keep actual full stored scope available in these exports even though list APIs project it. Record who requested an export and its selection/format/checksum, without storing secret configuration or rendering credentials.

CLI `export --party <uuid> --format pdf|csv`, `export --run <uuid> --format pdf|csv`, `export --all --format zip`, with an explicit output path. Training-pair export belongs to milestone 8; do not invent model labels here.

## Functional retention with permanent audit evidence

Default remains indefinite retention. A selected integer period is at least five years; `null` disables purging. The [verified EAR provision](https://www.ecfr.gov/current/title-15/subtitle-B/chapter-VII/subchapter-C/part-762/section-762.6) bases the horizon on the latest applicable transaction-related event and forbids destroying requested records without the agency's written authorization. Screening age alone is insufficient, because this app does not observe those external events. Administrative retention metadata must not become transaction or shipment screening.

Provide explicit Admin per-party retention eligibility metadata: latest applicable event date, who attested it, acknowledgment that relevant external dates were considered, and whether government holds have been excluded. Keep audit snapshots of each attestation. Initially purge only explicitly eligible inactive-party bundles; active-party history and unknown dates/hold status remain protected. Compute the age basis conservatively as the latest of the attested event date, last party activity/deletion, last screening and last disposition. Any newer activity resets eligibility. Reject future event dates. This keeps purging functional for actually eligible records while preserving ongoing business evidence.

Provide audited global/per-party legal holds with reason and actor. Hold placement and release are immutable events. A government-request hold cannot be released without recording a written-authorization reference; a generic no-hold attestation cannot override an active hold. Keep hold/eligibility history permanently. API: `GET/PATCH /retention/parties/{id}/eligibility`, `POST /retention/holds`, `POST /retention/holds/{id}/release`, `GET /retention/status`, Admin `POST /retention/preview` and `POST /retention/apply`; CLI `retention preview` and `retention apply` use the same service. Preview is reviewable information, not a new mandatory approval gate for every scheduled run.

Preserve `audit_log`, parties, listing revisions and completed run provenance permanently. Purge only eligible closed comparison/decision rows that have no retained operational or historical references. Active suppressions retain their original human decisions/hits. A retained hit's `queue_anchor_hit_id`, `prior_disposition_id` and `suppression_disposition_id` protect their referenced evidence even where SQLite does not express that dependency as a foreign key. Never delete open comparisons. Report dependency/hold blocks explicitly. Any inactive suppression deletion must be part of a specifically eligible dependency bundle and preserve its actual audit history; do not erase live false-positive memory.

The current unconditional hit/disposition delete guards must evolve through a migration into bounded capability checks, without dropping guards during a retention job. Register a connection-local SQLite `retention_delete_allowed(table_name, row_id)` function that returns false by default. Only the internal retention service, after a fresh writer-locked floor/date/hold/dependency check, can grant a frozen exact table-and-ID allowlist on that one connection for that one transaction. Ordinary app connections, raw SQLite connections, untrusted SQL, API body fields and boolean settings cannot enable it. Keep UPDATE guards unconditional; audit-log/party/revision/run deletion remains forbidden. Python's [SQLite function registration](https://docs.python.org/3.12/library/sqlite3.html) supports the connection callback.

The ORM deletion guard uses the same bounded internal context and exact object IDs, never a permissive session-wide boolean. Broad bulk deletes remain rejected; a statement attempting an unapproved ID must abort atomically at the SQL trigger. Clear capability state in `finally` and on pool check-in, including rollback/error paths. No privileged connection may return to the pool with grants remaining.

Insert an append-only purge certificate in the same transaction before deletion: policy/floor/cutoff, attestation/hold references, requested/actual IDs and hashes, counts, run/party links, actor or scheduled system identity, timestamp and manifest checksum. Deletion succeeds or the certificate and deletions roll back together. Audit evidence is never deleted or rewritten, even after a successful purge. This removes qualifying screening rows; it is not an erasure of audited customer information or a promise of reduced audit-storage size.

Party/run exports must distinguish purged comparison details from a genuine zero-hit run. Use actual retained purge certificates/audit snapshots to preserve the truth of the original comparison and its disposition. Never print `zero_hits=true` merely because eligible hit rows were later removed. Retained run counters and settings are immutable and must not be recomputed or edited after pruning.
